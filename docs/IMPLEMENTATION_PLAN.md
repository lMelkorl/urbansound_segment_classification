# Edge Audio V2 Implementation Plan

This plan preserves `urbansound_segment_task/goals/` and all committed historical results. Each phase is intended to be independently reviewable. A phase may add only the files needed by implemented behavior; the directory examples below are not instructions to create empty scaffolding.

## Global delivery rules

- Existing results remain labeled **Legacy single-split results** and are never overwritten.
- New metrics must be generated by committed code and point to a machine-readable run artifact.
- Every run directory is immutable or collision-protected and contains config, environment, split/model identity, raw data where applicable, and summaries.
- Dataset-, checkpoint-, network-, GPU-, and long-running operations require an explicit command and approval before execution.
- CPU benchmarks use the same machine and declared thread policy, with warm-up and raw samples.
- Training/evaluation, export, CLI, and demo share preprocessing and class-order contracts.
- Dataset-free unit tests are the default; dataset/model tests are explicitly marked.

## Phase 0 — Audit and reproducible environment

Status: audit and plan documentation complete; environment implementation intentionally deferred pending review.

### Small reviewable work

1. Preserve and review `docs/AUDIT.md` and this plan.
2. Add a read-only environment audit CLI and versioned environment-result schema.
3. Decide and document the supported Python/platform matrix and dependency groups.
4. Add project metadata and locked/tested dependency inputs without mass-upgrading legacy code.
5. Add dataset-free CI checks for imports, CLI `--help`, JSON schemas, and unit tests.
6. Later, clarify README legacy labels and broken commands only after provenance wording is approved.

### Expected files

- `docs/AUDIT.md`
- `docs/IMPLEMENTATION_PLAN.md`
- `docs/METHODOLOGY.md` (initial environment and provenance policy)
- `pyproject.toml` and reviewed lock/constraint files
- `urbansound_segment_task/edge_v2/utils/environment.py`
- `scripts/audit_environment.py`
- `tests/unit/test_environment.py`
- CI configuration
- `README.md` only for reviewed corrections; never metric replacement

### Acceptance criteria

- Original tag and legacy directories remain unchanged.
- A fresh supported environment can install declared groups deterministically.
- `python scripts/audit_environment.py --help` works with core dependencies only.
- The audit command writes schema-versioned Python/OS/CPU/package/thread metadata without network access.
- Unsupported/missing optional frameworks are reported, not imported unconditionally.
- No generated benchmark number appears in documentation.

### Tests

- Unit tests for environment schema, missing-package handling, redaction, and deterministic serialization.
- Fresh-environment install and CLI smoke test on the primary supported platform.
- Static checks for JSON, shell, Python syntax, and forbidden legacy-result modifications.

### Expected artifacts

- Small environment audit JSON under a versioned non-legacy result directory.
- Locked dependency inputs and an install matrix; no dataset/model/checkpoint artifacts.

### Risks and controls

- Framework/platform conflicts: choose a narrow tested Python baseline before locking.
- Accidental local-data capture: allowlist hardware/environment fields and test redaction.
- Legacy breakage from dependency changes: isolate legacy/training/export/demo extras and do not rewrite legacy imports.

### Resource requirements

- Dataset: no.
- GPU: no.
- Long-running CPU: no.
- Network: only for an explicitly approved dependency installation/lock resolution; audit runtime itself is offline.

## Phase 1 — CPU benchmark harness

### Small reviewable work

1. Define benchmark input, stage, timing-sample, hardware, model-artifact, and summary schemas.
2. Implement monotonic high-resolution timers, warm-up, percentile calculation, thread control, and raw-sample capture using a synthetic callable.
3. Add staged timing for decode, preprocessing, model inference, aggregation, and end-to-end execution.
4. Implement model adapters/preflight checks for YAMNet+LightGBM, ESResNeXt, and AudioCLIP without auto-downloads.
5. Benchmark each recoverable legacy inference path on one fixed sample manifest; mark unavailable methods with structured reasons.
6. Add comparison/report generation only from schema-valid artifacts.

### Expected files

- `urbansound_segment_task/edge_v2/benchmarks/{schema,timer,runner,system,report}.py`
- `urbansound_segment_task/edge_v2/models/{base,yamnet_lgbm,esresnext,audioclip}.py`
- `configs/edge_v2/cpu_benchmark.yaml`
- `scripts/run_cpu_benchmark.py`
- `docs/BENCHMARK_PROTOCOL.md`
- `tests/unit/test_benchmark_*.py`
- `tests/smoke/test_benchmark_cli.py`

### Acceptance criteria

- Synthetic benchmarks run without dataset or pretrained models.
- Timings use `perf_counter_ns` or an equivalent monotonic high-resolution source.
- Output records warm-up/timed iterations, batch size, threads, sample rate, window/overlap, decode inclusion, cold/load times, p50/p95/p99 where valid, segments/s, real-time factor, peak RSS, runtime, precision, model size/hash, and hardware/software metadata.
- Raw samples reproduce the summary percentiles.
- Every adapter fails clearly when a local artifact/dependency is absent and never downloads during import or benchmark.
- Comparisons never mix GPU and CPU values in an unlabeled column.

### Tests

- Fake-clock/timer tests, percentile edge cases, warm-up exclusion, stage accounting, schema validation, thread-setting round trip, and artifact hashing.
- CLI `--help` and synthetic benchmark smoke tests.
- Optional marked single-sample adapter tests when local artifacts exist.

### Expected artifacts

- `results/cpu_benchmarks/<schema-version>/<run-id>/{config,environment,raw_timings,summary}.json`
- Availability/preflight report for all three legacy methods.
- Actual benchmark fields remain `TBD` until an approved run occurs.

### Risks and controls

- OS-specific memory/counter behavior: adapter layer plus platform-specific tests.
- Thermal/background-process noise: documented run conditions and repeated samples.
- Oversubscription: explicit, persisted thread settings and conservative defaults.
- Irrecoverable AudioCLIP source: structured unavailable result, never fabricated replacement.

### Resource requirements

- Dataset: a small approved local sample manifest for real model runs; no dataset for harness tests.
- GPU: no; CPU is mandatory for final measurements.
- Long-running CPU: no for synthetic tests; moderate for full legacy inference benchmark.
- Checkpoints/network: local verified artifacts required; any acquisition requires separate approval.

## Phase 2 — Correct cross-fold evaluation

### Small reviewable work

1. Validate UrbanSound8K metadata schema, class mapping, files, and official folds.
2. Define deterministic per-test-fold validation policy and emit split manifests before model work.
3. Centralize and version segmentation, short/tail policy, preprocessing, clip identity, and class order.
4. Centralize probability/logit aggregation and metrics with invariant checks.
5. Implement resumable fold orchestration with isolated run directories and test-fold gating.
6. Validate on synthetic metadata, then a dataset index dry run, then one approved fold smoke run.
7. Run all folds only after review of the smoke artifact and resource command.

### Expected files

- `urbansound_segment_task/edge_v2/data/{index,splits,manifest}.py`
- `urbansound_segment_task/edge_v2/evaluation/{segmentation,aggregation,metrics,runner,schema}.py`
- `configs/edge_v2/cross_fold.yaml`
- `scripts/run_cross_fold.py`
- `docs/METHODOLOGY.md`
- `tests/unit/test_{splits,segmentation,aggregation,metrics}.py`
- `tests/integration/test_cross_fold_synthetic.py`

### Acceptance criteria

- Each of ten official folds becomes test exactly once.
- Validation policy is deterministic, declared, and leaves train/validation/test clip keys disjoint.
- Split manifests record metadata/file identity, seed, policy, counts, and hashes.
- Segment and clip accuracy/macro-F1, full-label per-class metrics, and confusion matrices are emitted per fold.
- Aggregate output reports mean and standard deviation across folds and links every input artifact.
- Resume cannot mix configurations, model hashes, splits, or stale checkpoints.
- Single-split legacy and cross-fold results are never presented as directly equivalent.

### Tests

- Property/invariant tests for fold and clip disjointness, complete test-fold coverage, deterministic manifests, class order, short/tail behavior, and aggregation.
- Synthetic end-to-end cross-fold test with known predictions.
- Dataset inventory dry run and one-fold smoke test when approved.

### Expected artifacts

- `results/cross_fold/<model>/<run-id>/split_manifests/*.json`
- Per-fold configs, predictions or sufficient trace data, metrics, per-class CSV/JSON, confusion arrays/images, durations, checkpoints references, and aggregate summary.

### Risks and controls

- Compute multiplication across ten folds: resume/checkpoint policy and staged one-fold approval.
- Changed segmentation invalidating comparison: version policy and retain explicit legacy mode only for reproduction.
- Test-guided tuning: freeze configuration/model-selection policy before held-out evaluation.

### Resource requirements

- Dataset: yes for inventory and real evaluation.
- GPU: not required for pipeline tests; likely useful/required for practical full teacher training.
- Long-running CPU: yes if CPU-only training/evaluation is selected.
- Checkpoints: local verified artifacts for pretrained methods.

## Phase 3 — Compact CPU model

### Small reviewable work

1. Implement content-addressed, non-committed YAMNet embedding cache with manifest validation.
2. Establish LightGBM as the compact-candidate baseline under the Phase 2 split protocol.
3. Add a small MLP, then temporal convolution, then lightweight attention pooling one at a time.
4. Record parameters, native serialized size, latency, throughput, peak memory, accuracy, and macro-F1 through shared schemas.
5. Add ablations only when they answer a specific design question.
6. Select the Pareto candidate using a predeclared policy, not accuracy alone.

### Expected files

- `urbansound_segment_task/edge_v2/features/{yamnet,cache,manifest}.py`
- `urbansound_segment_task/edge_v2/models/{lightgbm,mlp,temporal_conv,attention_pool}.py`
- `urbansound_segment_task/edge_v2/training/{trainer,selection}.py`
- candidate config files under `configs/edge_v2/`
- `scripts/run_compact_experiment.py`
- unit and smoke tests for caches/models/training

### Acceptance criteria

- Cache keys include source audio identity, preprocessing/model identity, and configuration.
- Cache writes are atomic, validated, and ignored by Git.
- Every candidate uses identical folds/features/evaluation and produces a model card fragment plus benchmark link.
- Parameter count and serialized size are computed by committed code.
- Candidate selection is reproducible from machine-readable artifacts.
- Missed target values are reported honestly.

### Tests

- Cache invalidation/collision/corruption tests.
- Tensor shape, padding/mask, determinism, save/load parity, tiny overfit, and interrupted-run resume tests.
- One-fold smoke training before any full cross-fold run.

### Expected artifacts

- Non-committed cached embeddings plus committed small manifests.
- `results/compact_model/<candidate>/<run-id>/` configs, histories, metrics, model identity, sizes, benchmarks, and comparison summary.
- Large checkpoints remain uncommitted.

### Risks and controls

- Storage growth and stale features: content addressing, quota guidance, and manifest validation.
- Segment leakage through cached features: split-independent extraction plus manifest-level clip checks.
- Architecture creep: sequential candidates and evidence-gated complexity.
- YAMNet extraction dominates edge runtime: benchmark end-to-end and retain an end-to-end small CNN fallback decision point.

### Resource requirements

- Dataset: yes.
- GPU: optional for feature extraction/teacher experiments; compact training must support CPU.
- Long-running CPU: yes for full feature extraction and cross-fold candidates.
- Checkpoint/network: verified local YAMNet asset required; acquisition needs approval.

## Phase 4 — ONNX and quantization

### Small reviewable work

1. Export the selected compact classifier to ONNX with embedded contract metadata.
2. Compare native and ONNX outputs on deterministic representative inputs.
3. Benchmark ONNX FP32 through the Phase 1 harness.
4. Attempt dynamic INT8, then static INT8 only with a declared calibration split.
5. Use QAT only if measured degradation justifies it.
6. Re-run exact-artifact accuracy and CPU benchmarks before selection.

### Expected files

- `urbansound_segment_task/edge_v2/export/{onnx,quantize,validate}.py`
- `scripts/{export_onnx,validate_export}.py`
- export/quantization configs
- parity and quantization tests
- deployment section in `docs/MODEL_CARD.md`

### Acceptance criteria

- Exported input/output/class/preprocessing contracts are explicit.
- Native-versus-ONNX tolerance is predeclared and validated on representative samples.
- Accuracy/macro-F1 belongs to the exact hashed exported artifact.
- FP32/INT8 size, memory, p50/p95/p99, throughput, and real-time factor are measured on the same CPU.
- INT8 acceleration is claimed only if measured; unsupported operators/platforms are recorded.

### Tests

- Export CLI smoke, dynamic shape/batch tests, output parity, corrupted artifact handling, calibration train/test separation, and schema linkage.

### Expected artifacts

- Uncommitted or release-managed hashed ONNX FP32/INT8 models.
- `results/quantization/<run-id>/` parity samples, calibration manifest, exact-artifact metrics, raw timings, and summary.

### Risks and controls

- Numerical/accuracy drift: tolerance gates and exact-artifact evaluation.
- Calibration leakage: training-only calibration manifest and assertions.
- Hardware-dependent INT8 benefit: report target CPU/runtime details and keep FP32 fallback.

### Resource requirements

- Dataset: representative validation/test data and training-only calibration data.
- GPU: no.
- Long-running CPU: moderate for exact-artifact evaluation and repeated benchmarks.
- Additional runtime dependencies: ONNX/ONNX Runtime, installed only after review.

## Phase 5 — Live offline demo

### Small reviewable work

1. Build a headless runtime API for file/array sliding-window inference and rolling metrics.
2. Add confidence threshold and `unknown`/`uncertain` behavior.
3. Add file CLI and test it fully offline.
4. Add microphone capture with permission/device failure handling.
5. Choose the smallest suitable local UI after measuring dependency cost, then add timeline/status views.
6. Verify no runtime network access and package the model/config/class map together.

### Expected files

- `urbansound_segment_task/edge_v2/runtime/{pipeline,audio,streaming,status}.py`
- `urbansound_segment_task/edge_v2/demo/` implementation
- `scripts/run_demo.py`
- demo config and runtime tests
- demo section in `docs/MODEL_CARD.md`

### Acceptance criteria

- Live microphone and file upload work on CPU without network or cloud APIs.
- Runtime uses the same preprocessing, class order, aggregation, and hashed model as evaluation.
- UI shows current class, confidence, timeline, CPU/runtime/precision/model size, rolling p50/p95, segments/s, and real-time factor.
- Missing permission/device/file/model errors are actionable and do not crash silently.
- Threshold is configurable and low-confidence output is not forced into a known class.

### Tests

- Headless file/array golden tests, streaming chunk-boundary tests, rolling-stat tests, threshold tests, missing-permission/device mocks, and offline/no-network smoke test.

### Expected artifacts

- Reproducible local demo config and small synthetic/example audio permitted for distribution.
- Demo run metadata and instructions for recording 30-60 seconds of evidence; no sensitive recordings.

### Risks and controls

- UI/runtime preprocessing drift: UI calls only the headless runtime.
- Audio backend differences: explicit supported matrix and graceful fallback.
- Confidence misinterpretation: visible uncertainty behavior and model-card limitation.
- Dependency bloat: evaluate Streamlit/Gradio/lightweight web options before selecting one.

### Resource requirements

- Dataset: no for ordinary demo operation.
- GPU: no.
- Long-running CPU: no; must sustain real time on the documented target CPU.
- Microphone permission: yes for live mode; file mode remains available.

## Phase 6 — Robustness tests and final documentation

### Small reviewable work

1. Implement deterministic perturbations for clean, 20/10/0 dB SNR noise, gain, time shift, and selected resampling/codec conditions.
2. Validate perturbation math and preserve clean references.
3. Run robustness evaluation through the exact exported runtime artifact.
4. Aggregate degradation by condition/class/fold without mixing a manual recording set into training.
5. Finalize methodology, benchmark protocol, results, model card, README, and reproduction commands from artifacts.
6. Add demo evidence instructions and a release checklist.

### Expected files

- `urbansound_segment_task/edge_v2/evaluation/{perturbations,robustness}.py`
- `scripts/run_robustness.py`
- robustness configs and tests
- `docs/{METHODOLOGY,BENCHMARK_PROTOCOL,MODEL_CARD,RESULTS}.md`
- `README.md`

### Acceptance criteria

- Perturbations are seeded, parameterized, and tested at requested SNR/gain/shift/resampling conditions.
- Clean metrics match the same exact-artifact evaluation path within declared tolerance.
- Reports show accuracy/macro-F1 degradation by condition and preserve fold/class detail.
- Manual recordings, if approved, are clearly separated with recording conditions and limitations.
- Every README number links to a machine-readable artifact; unavailable runs are `TBD`.
- Reproduction commands declare resources and never auto-download large assets during runtime.

### Tests

- SNR numerical tests, gain/time-shift/resampling invariants, seeded determinism, input immutability, schema/aggregation tests, documentation link/provenance checks, and clean-path regression.

### Expected artifacts

- `results/robustness/<artifact-hash>/<run-id>/` configs, condition manifests, per-fold/class metrics, degradation summaries, and provenance.
- Final documentation and release checklist.

### Risks and controls

- Artificial robustness overclaims: describe perturbations as controlled tests, not real-world representativeness.
- Codec/platform variance: persist encoder/runtime versions or omit unsupported conditions.
- Documentation drift: generate tables from validated artifacts and test links/schema references.

### Resource requirements

- Dataset: yes for representative full evaluation.
- GPU: no for exported CPU artifact evaluation.
- Long-running CPU: yes for the full condition-by-fold matrix.
- Manual recordings: optional and only with explicit approval and privacy review.

## First proposed implementation task after approval

Implement only the dataset-free environment/benchmark foundation:

1. Add a schema-versioned, allowlisted environment collector.
2. Add `scripts/audit_environment.py` with `--help`, `--output`, and offline operation.
3. Add unit tests for deterministic schema output, missing optional packages, and sensitive-value exclusion.
4. Write one non-benchmark environment JSON to a new run-scoped directory and validate it.

This task is small, CPU-light, requires no dataset/checkpoint/GPU/network, does not touch model code or legacy results, and supplies the hardware/runtime provenance required before the Phase 1 timer and model adapters can produce defensible measurements.
