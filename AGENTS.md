# AGENTS.md — UrbanSound Edge Audio V2

## 1. Project context

This repository began as a technical case study for segment-based environmental sound classification on UrbanSound8K.

The current repository contains three approaches:

1. **YAMNet embeddings + LightGBM**
2. **ESResNeXt-fbsp fine-tuning**
3. **AudioCLIP audio-branch fine-tuning**

The existing results were primarily produced on an NVIDIA A100 40 GB GPU. The current README reports segment-level and clip-level metrics, training durations, and selected GPU throughput measurements.

The original work successfully satisfied the case-study requirements. This new phase is not a rewrite of the old case. It is a research-and-engineering extension inspired by a practical question raised after the original study:

> How fast and useful are these approaches on CPU-only hardware?

The goal is to turn the original prototype into a reproducible, deployable, CPU-first edge-audio system with scientifically defensible evaluation.

---

## 2. Core product and research vision

Build an **offline, CPU-first environmental sound classification system** that:

- Processes live microphone input and uploaded audio files.
- Runs without a GPU and without an internet connection.
- Reports real latency, throughput, memory usage, model size, and accuracy.
- Uses the official UrbanSound8K folds correctly.
- Includes a compact optimized model suitable for ordinary laptops and edge-class CPUs.
- Preserves the original three approaches as historical baselines.
- Produces results that another engineer can reproduce.

The intended “wow” factor is not an unsupported claim of state-of-the-art accuracy.

The intended contribution is:

> A small, measurable, reproducible model that preserves strong classification quality while providing practical CPU inference, low memory use, and a working real-time demo.

## 4. Scientific integrity

### 4.1 Existing results

Treat the current Fold 1–8 training, Fold 9 validation, Fold 10 test setup as a **legacy single-split experiment**.

Do not describe it as a complete 10-fold cross-validation benchmark.

Preserve the existing values and label them clearly as:

```text
Legacy single-split results
```

### 4.2 New official evaluation

Implement fold-wise evaluation that respects the predefined UrbanSound8K folds.

For every test fold:

- Use one official fold as the test set.
- Select validation data without mixing segments from the same original clip across train, validation, and test.
- Use all remaining allowed folds for training.
- Record the exact split policy in machine-readable output.
- Aggregate results across all test folds.

Report at minimum:

- Mean clip accuracy.
- Standard deviation of clip accuracy.
- Mean clip macro-F1.
- Standard deviation of clip macro-F1.
- Segment accuracy and macro-F1.
- Per-class precision, recall, and F1.
- Confusion matrix.
- Random seed.
- Package versions.
- Hardware details.
- Model configuration.
- Training duration.

Never compare a single-fold result directly with a published cross-fold mean without an explicit warning.

### 4.3 No metric invention

Do not place a number in README tables unless it was generated by a committed benchmark script and is traceable to a result artifact.

Every reported metric must reference a JSON or CSV file.

Use `TBD` when a benchmark has not yet been executed.

## 5. CPU benchmark specification

Benchmark the relevant models on the same CPU machine and under the same conditions.

At minimum evaluate:

- YAMNet embedding extraction.
- YAMNet + LightGBM end-to-end inference.
- ESResNeXt inference when technically feasible.
- AudioCLIP inference when technically feasible.
- The new compact EdgeSound model.
- FP32 and INT8 versions of the compact model.

For every benchmark, record:

- CPU model.
- Operating system.
- Python version.
- Runtime/backend.
- Physical and logical core count.
- Configured thread count.
- Batch size.
- Input sample rate.
- Window duration.
- Overlap.
- Warm-up iterations.
- Timed iterations.
- Model load time.
- Cold-start latency.
- Batch-1 p50 latency.
- Batch-1 p95 latency.
- Batch-1 p99 latency where practical.
- Segments per second.
- Real-time factor.
- Peak resident memory.
- Model file size.
- Accuracy and macro-F1 for the exact exported artifact.

Benchmarking rules:

- Separate preprocessing, model inference, aggregation, and full-pipeline timings.
- Use monotonic high-resolution timers.
- Run warm-up iterations before recording measurements.
- Avoid including model download time.
- State whether audio decoding is included.
- Pin or explicitly report thread settings.
- Do not compare GPU throughput with CPU throughput in the same column without hardware labels.
- Save raw timing samples as machine-readable artifacts.

The current segmentation convention is approximately:

- Window: 0.96 seconds.
- Overlap: 50%.

A system only needs to process slightly more than two windows per second to keep up with real time. Report the achieved multiple of real time, not only segments/second.

## 6. New compact model

Create a genuinely lightweight CPU-oriented model rather than merely running the existing heavy models on CPU.

Begin with a technical comparison and choose the simplest defensible path. Candidate directions include:

### Preferred practical path

- Cache YAMNet embeddings.
- Train a compact temporal classifier over segment embeddings.
- Compare:
  - LightGBM baseline.
  - Small MLP.
  - Temporal convolution network.
  - Lightweight attention pooling.
- Export the selected model into a portable CPU runtime.

### Alternative end-to-end path

Use a compact audio architecture such as a small MobileNet-style spectrogram CNN or another justified edge-audio model.

### Optional distillation path

Use ESResNeXt or another strong pretrained model as a teacher and distill knowledge into the compact student.

Do not introduce architectural complexity unless an ablation demonstrates its value.

For each candidate, compare:

- Accuracy.
- Macro-F1.
- Parameter count.
- Serialized model size.
- CPU latency.
- CPU throughput.
- Peak memory.

The selected model should optimize the Pareto trade-off rather than accuracy alone.

## 7. Optimization and export

The compact model should support a practical CPU deployment format.

Preferred target:

- ONNX.
- ONNX Runtime CPU.

Evaluate where supported:

- FP32.
- Dynamic INT8 quantization.
- Static INT8 quantization.
- Quantization-aware training only if post-training quantization causes unacceptable degradation.

Export requirements:

- Provide a validation script that compares native-framework and exported-model outputs.
- Define an acceptable numerical tolerance.
- Verify the exported model on representative samples.
- Report the accuracy of the exported artifact, not only the pre-export model.
- Keep preprocessing identical between training, evaluation, CLI, and demo.

Do not claim INT8 acceleration unless measured on the target CPU.

## 8. Real-time offline demo

Create a simple but credible local demo.

Required capabilities:

- Live microphone input.
- Audio-file upload.
- Sliding-window inference.
- Clip/timeline visualization.
- Current predicted class.
- Confidence score.
- Rolling latency and throughput.
- CPU-only operation.
- No required cloud service.
- No required external API.
- Graceful handling of missing microphone permissions.
- Configurable confidence threshold.
- `unknown` or `uncertain` output below the threshold.

Display a small runtime status panel containing:

```text
CPU only
Runtime
Precision: FP32 or INT8
Model size
p50/p95 latency
Segments per second
Real-time factor
```

Prefer a maintainable local interface over a visually elaborate application. A small Streamlit, Gradio, or lightweight web application is acceptable after evaluating repository fit and dependency cost.

## 9. Robustness evaluation

UrbanSound8K alone is not sufficient to demonstrate practical behavior.

Add a controlled robustness suite:

- Clean audio.
- Added noise at several SNR levels.
- Gain variation.
- Time shift.
- Resampling or codec degradation where appropriate.

Suggested noise levels:

```text
20 dB SNR
10 dB SNR
0 dB SNR
```

Report accuracy/macro-F1 degradation by condition.

Allow a small manually recorded evaluation set, but:

- Do not mix it into UrbanSound8K training.
- Do not report it as a statistically representative benchmark.
- Document recording conditions and limitations.
- Do not commit sensitive recordings without explicit approval.

## 11. Engineering standards

Use:

- Typed Python where practical.
- Small focused modules.
- Configuration files instead of duplicated constants.
- Deterministic seeds where supported.
- Structured logging.
- Clear error messages.
- Unit tests for critical transformations.
- Smoke tests for CLI entry points.
- Machine-readable result artifacts.
- Relative repository paths.
- Platform-aware code for macOS, Linux, and Windows where practical.

Avoid:

- Notebook-only logic.
- Hidden state.
- Hardcoded local paths.
- Silent exception handling.
- Global mutable configuration.
- Duplicate preprocessing implementations.
- Downloading large assets during import.
- Unbounded multiprocessing defaults.
- Tests that require the full dataset unless marked explicitly.

All public commands should support `--help`.

## 12. Dependency policy

Before changing dependencies:

1. Audit the current environment and imports.
2. Separate training-only, benchmark-only, and demo dependencies where useful.
3. Avoid unnecessary heavy frameworks.
4. Pin versions sufficiently for reproducibility.
5. Document any platform-specific limitations.

Do not perform an unreviewed mass upgrade of all dependencies.

If old dependencies conflict with a modern CPU runtime, propose a migration plan before rewriting working legacy code.

## 14. Target success criteria

Treat the following as aspirational engineering targets, not guaranteed results:

- INT8 model size below 10–20 MB.
- Batch-1 p95 CPU inference below 100 ms on a documented modern laptop CPU.
- At least 10× real-time processing where feasible.
- Clip-level macro-F1 within approximately 1–3 percentage points of the strongest validated teacher/baseline under the same split protocol.
- Complete 10-fold mean and standard deviation reporting.
- Fully offline demo.
- One-command CPU benchmark.
- No untraceable README metrics.

If a target is missed, report the result honestly and explain the bottleneck.

## 15. Non-goals

Do not optimize for:

- A sensational “world record” claim.
- Inflated results from random train/test splits.
- Dataset leakage.
- A huge UI before the benchmark is trustworthy.

- GPU-only success.
- Replacing all legacy code without evidence.
- Premature micro-optimization.
- Adding many models without a clear research question.

## 16. Required workflow for Codex

For every substantial task:

1. Inspect the relevant code and current result artifacts.
2. State assumptions.
3. Make the smallest coherent change.
4. Add or update tests.
5. Run the narrowest meaningful validation.
6. Record commands and outcomes.
7. Do not claim success when dataset/checkpoints/hardware are unavailable.
8. Distinguish:
   - Code completed.
   - Smoke-tested.
   - Fully benchmarked.
   - Awaiting dataset or long-running experiment.

Do not begin expensive training automatically.

Before any operation expected to take significant compute or download large files:

- Provide the exact command.
- Estimate required resources qualitatively.
- Explain expected output artifacts.
- Wait for explicit user approval.
